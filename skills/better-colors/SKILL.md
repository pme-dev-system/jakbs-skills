# OKLCHカラー

OKLCHは、明度・彩度・色相がデザイン上の制御として機能する、知覚的に均一な色空間である。プロジェクトがすでにOKLCHを使っている場合、新しい色システムを構築する場合、またはユーザーが変換やパレット作業を求めている場合に使用する。それ以外では、プロジェクトが確立したトークンと表記法を維持する。単発の修正のために第二の色表現を持ち込むより、一貫したhexまたはRGBトークン体系の方が望ましい。インタラクティブに試すには[oklch.fyi](https://oklch.fyi)を参照。

## Core Principles

### 1. 知覚的な色空間を使う

- **既存のシステムを尊重する。** このスキルが読み込まれたという理由だけで表記法を変換しない。タスクに色システムの移行が含まれない限り、プロジェクトのセマンティックトークンと記述形式を再利用する。
- **知覚的均一性。** Lのステップが等しければ明るさも等しい。`oklch(0.5 ...)`は視覚的に中間になる。HSLの`lightness: 50%`は色相によって大きく変動する。
- **安定した色相。** HSLの青は明度が変化すると紫寄りにシフトする。OKLCHの色相は明度の全範囲で一定を保つ。
- **独立した彩度(chroma)。** 彩度(chroma)は明度に依存しない、色の鮮やかさの絶対的な尺度である。HSLの彩度(saturation)は明度に依存する。
- **有限の色域。** すべてのoklch値が表示可能なsRGBカラーに対応するわけではない。特定の色相で彩度(chroma)が高い値はクリップする。色域への意識が必要。

### 2. OKLCHの表記形式を統一する

```
oklch(L C H)
oklch(L C H / alpha)
```

| チャンネル | 範囲 | 説明 |
| --- | --- | --- |
| L (明度) | 0–1 | 0 = 黒、1 = 白。知覚的に均一。 |
| C (彩度/chroma) | 0–~0.4 | 色の鮮やかさ。0 = グレー。最大値はLとHに依存する。 |
| H (色相) | 0–360 | 度単位の色相角。 |
| alpha | 0–1 | 任意の透明度。スラッシュ構文。 |

```css
oklch(0.637 0.237 25.331)
oklch(0.8 0.05 200 / 0.5)
```

LとCは小数点以下3桁、Hは最大3桁を使う。末尾のゼロは省略し、`-0`は`0`と表記する。OKLCHはBaseline 2023である。サポート要件が特に広範な場合は、固定のグローバルカバレッジ率に頼るのではなく、対象プロジェクトのブラウザマトリクスを確認する。

### 3. コントラスト、色域、パレットの挙動を測定する

| ルール | 値 |
| --- | --- |
| ライト/ダークの境界 | L > 0.73 = 明るい背景 → 暗いテキスト。それ未満では、明るいテキストの方が依然としてスコアが高い |
| 明度差(明るい背景) | 背景のLが0.9超のとき、前景のLは0.35未満 |
| 明度差(暗い背景) | 背景のLが0.25未満のとき、前景のLは0.9超 |
| 色相ドリフトの閾値 | パレットのステップ間で10°を超える広がり = 目に見えるドリフト |
| APCA本文テキスト | \|Lc\| >= 75が最低限、>= 90が推奨 |
| APCA非本文テキスト | \|Lc\| >= 60が最低限 |
| WCAG 2通常テキスト | 4.5:1 AA、7:1 AAA |
| コントラストの修正(依頼時のみ) | まずLを調整する。可能な限りCとHは維持し、その後レンダリングされたペアを再測定する |

## Common Mistakes

| 問題 | 修正 |
| --- | --- |
| 生の色値がプロジェクトのセマンティックトークン体系を迂回している | プロジェクトの既存の表記法で、正しいロールのトークンを再利用または追加する |
| hex/RGBのコードベースに単発のOKLCH値が持ち込まれている | タスクに色システムの移行が含まれない限り、確立された表記法を維持する |
| 色相ドリフトのあるHSLパレットの階調 | oklchの色相を一定にして再構築する |
| コントラスト不合格(APCAで前景とその背景を確認) | ペア、測定したLc、満たせなかった閾値を報告する。色の変更は依頼された場合のみ行う(その際はLを調整し、CとHは維持する) |
| 色域チェックなしの高彩度 | sRGBにおけるそのL/Hでの最大彩度にクランプする |
| 異なる色相間で絶対Cの値が同じ | 鮮やかさを一定に保つため、同じC%(最大値に対する割合)を使う |
| sRGBフォールバックのないP3カラー | `@media (color-gamut: p3)`パターンを追加する |
| ライトパレットを機械的に反転させて作ったダークモード | ライトパレットを出発点にし、彩度と明度を調整したうえで、すべての前景/背景ペアを再チェックする |
| Tailwind v4の`@theme`内のhex | oklch値に変換する |
| カンマ構文のアルファ | スラッシュを使う: `oklch(L C H / alpha)` |
| 同じ色相が2つの異なる意味を持つ(リンクの色が装飾目的で再利用されている) | 1つの色には1つの意味。2つ目の用途にはニュートラルカラーを割り当てる |
| セマンティックトークンが本来のロール外で使われている(セパレーターをテキストとして使用) | 不足しているロール用のトークンを追加する。値が近いという理由で流用しない |
| 1つの画面内に複数の色付きコントロール背景がある | 単一の主要アクションのみを塗りつぶす。副次的なものはニュートラルのままにする |
| ライトモードのみで検証されたパレット | 両方の見た目で、すべての前景/背景ペアを再チェックする |

## Review Output Format

このフォーマットは、ユーザーが単独の色レビューを求めた場合にのみ使用する。`better-interface`がレビューを統括する場合は、そのスキルにドメインの根拠と所見を提供し、出力フォーマット、重大度スケール、統合ルール、上限、判定はそちらを優先させる。

単独レビューは2つのパートで構成する。

### 所見

確認済みの所見はすべて原則ごとにグループ化する。**重大度**、**場所**、**変更前**、**変更後**、**理由**の列を持つMarkdownの表を使う。「変更前:」「変更後:」を別々の行で書くことは絶対にしない。

- **重大度**: `HIGH`はコンテンツを判読不能にするか、誤解を招くセマンティックカラーを割り当てるもの。`MEDIUM`は目に見えるテーマ、色域、または一貫性の失敗を生むもの。`LOW`は局所的な仕上げ。
- **場所**: `path/to/file:line`の形式で示す。アーティファクトにソースファイルがない場合は、代わりに画面とコンポーネントを正確に示す。
- **変更前 / 変更後**: 現在の値やトークンと、正確な置き換え内容を示す。
- **理由**: 違反した原則を明示し、該当する場合は測定したコントラストや色域の根拠を含める。

繰り返し発生するシステム的な問題は1行にまとめ、影響を受けたすべての場所を列挙する。所見のない原則は省略する。

| 重大度 | 場所 | 変更前 | 変更後 | 理由 |
| --- | --- | --- | --- | --- |
| MEDIUM | `src/theme.css:18` | `color: #3b82f6` | `color: oklch(0.623 0.188 259.815)` | 新規プロジェクトの色にはOKLCHトークンを使う |
| MEDIUM | `src/palette.ts:31` | 色相間で絶対Cの値が同じ | 各色相の最大彩度に対する同じC% | 彩度の値が同じでも、色相が異なれば鮮やかさは等しく見えない |
| HIGH | `src/theme.css:52` | フォールバックのないP3カラー | `@media (color-gamut: p3)`の前にsRGBフォールバックを追加する | この色はP3非対応ディスプレイで表示できない |

### 検証と判定

所見の後に:

1. **検証**: 実施した正確なチェックとその観察結果を列挙する。該当する場合はコントラストの測定値、色域チェック、ライトとダーク両方の見た目を含める。チェックを実施していない場合は、まだ検証が必要な内容を明記する。
2. **判定**: `HIGH`の所見が1つでも残っていれば`Block`。`MEDIUM`または`LOW`の所見のみが残っていれば`Needs changes`。対応が必要な所見が残っていない場合のみ`Approve`。

所見がない場合は、表を省略し「アクションが必要な色の所見はなし」と明記し、検証内容を報告したうえで`Approve`で締めくくる。
